# 【手順2】各テーブルの「属性（カラム）」を洗い出す

## カラムの作成方法
各テーブルの「属性（カラム）」を洗い出す
それぞれの箱（テーブル）に**「どんな情報を持たせるか」**を書き出します。

⚬「主キー（`id`）」を必ず全テーブルにつける  
⚬「1対多」で特定した**外部キー（相手のID）**を「多」側に持たせる  
⚬「多対多」の２つのキーを外部キーとして中間テーブルに持たせる  
⚬ 仕様書や要件から「タイトル」「時間」「再生数」などの必要な項目を割り振る


```
完成したカラム

### 1. channels（チャンネル）
- id
- name（チャンネル名：例「ドラマ1」）

### 2. genres（ジャンル）
- id
- name（ジャンル名：例「アニメ」「映画」）

### 3. programs（番組）
- id
- title（番組タイトル）
- description（番組詳細）

### 4. program_genres（番組ジャンル中間テーブル）
- id
- program_id（外部キー）
- genre_id（外部キー）

### 5. seasons（シーズン）
- id
- program_id（外部キー）
- season_number（シーズン番号：例「1」）
- name（シーズン名：例「竈門炭治郎 立志編」）

### 6. episodes（エピソード）
- id
- season_id（外部キー）
- episode_number（話数：例「1」）
- title（エピソードタイトル）
- description（エピソード詳細）
- duration（動画の時間／尺）
- release_date（公開日／公開年）

### 7. channel_schedules（番組枠 / 放送スケジュール中間テーブル）
- id
- channel_id（外部キー）
- episode_id（外部キー）
- start_time（放送開始時間）
- end_time（放送終了時間）
- view_count（★KPI：この放送枠での視聴数）
```

<details>
<summary>疑問：KPIとして、チャンネルの番組枠のエピソードごとに視聴数を記録する、つまり視聴数を記録する最小単位は”エピソード”ではないのか？  </summary>

結論から言うと「最小単位」は「エピソード」単体ではなく
**「（チャンネル × 番組枠 × エピソード）の組み合わせ」**になります！
なぜなら「同じエピソード（動画）でも、放送される『枠』が違えば、視聴数は別モノになるから」です。

分かりやすく「鬼滅の刃 第1話（エピソード）」で考えてみましょう！

### 💡 もし「エピソード」自体に視聴数を記録したら？

episodes（エピソード）テーブルにview_count（視聴数）を置いた場合、データはこうなります。

- 鬼滅の刃 第1話 ➔ 視聴数：13,000回

これだと、「第1話が全部で何回見られたか」の合計はわかりますが、「どの番組枠で何回見られたか」が消えてしまいます。

### 💡 仕様書が求めていること

仕様書の文章にある「チャンネルの番組枠のエピソードごとに視聴数を記録する」
ここには、単に「エピソードごとに」とは書かれておらず、頭に「チャンネルの番組枠の」**とついていますよね！

これは、以下のような意味になります。

- 8月1日 20:00〜【アニメ1CHの枠】で流した「第1話」 ➔ 10,000回
- 8月2日 14:00〜【ドラマ1CHの枠（再放送）】で流した「第1話」 ➔ 3,000回
**（チャンネル × 番組枠 × エピソード）の組み合わせ**

このように、「どのチャンネルの、どの時間の枠で放映された第1話か」という『放送枠（channel_schedules）』ごとに視聴数が生まれるんです！

### 🔑 まとめ

- エピソード（動画データそのもの） ＝ 視聴数は持たない（何度放送されても動画自体は1つだから）
- 番組枠（channel_schedules） ＝ ここに視聴数を記録する！（「この枠で流した時に何人見に来たか」を記録するため）
