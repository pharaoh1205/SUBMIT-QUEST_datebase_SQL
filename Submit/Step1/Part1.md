# 【手順1】問題文から名詞、それらのリレーション関係を書き出す

## ❶名詞を書き出す

```jsx
名詞
1.channels（チャンネル）
2.genres（ジャンル）
3.programs（番組）
4.program_genres（番組ジャンル中間テーブル）
5.seasons（シーズン）
6.episodes（エピソード）
7.channel_schedules（番組枠）
```

<details>
<summary>名詞を紙に書き出したらprogram_genresだけ思いつかなかった  </summary>

紙に書き出しても `program_genres` が出てこないのは当然なんです。
なぜなら、`program_genres` は現実世界にある「モノ（名詞）」ではなくデータベースの都合で生まれた「仕掛け（関係性）」だからです

**💡 中間テーブル（橋渡し役）が必要な理由**

例えば、ノートの1行に以下のように書いたとします。

- **番組**: 鬼滅の刃
- **ジャンル**: アニメ, アクション, ファンタジー

人間ならこれを見れば「なるほど3つのジャンルがあるんだな」と直感で理解できますよね。しかしデータベースは「1つのマス（カラム）には1つの値しか入れられない」というルール（正規化）があります。
1つのマスに「アニメ, アクション, ファンタジー」とカンマ区切りで詰め込むと、後から「アニメジャンルの番組だけ検索したい」となった時にDBが正しく検索できなくなってしまうのです。

**じゃあどうやって紐づける？**
番組テーブルとジャンルテーブルを直接繋ごうとすると、お互いに相手を複数持ってしまう（多対多の関係）ので、どっちのテーブルに相手のIDを書けばいいかパニックになります。そこで、「番組とジャンルのペアだけをメモする専門の紙」を1枚用意します。それが中間テーブルです！

【 program_genres（番組とジャンルのメモ帳）】

| program_id (番組) | genre_id (ジャンル) |
| :--- | :--- |
| 鬼滅の刃 (1) | アニメ (10) |
| 鬼滅の刃 (1) | アクション (11) |
| 鬼滅の刃 (1) | ファンタジー (12) |


こうやって「1行につき1つのペア」で書けば、DBのルールを守ったまま「鬼滅の刃は3つのジャンルを持っている」という事実をカンペキに表現できます。

**🔍 DB設計での名詞の探し方のコツ**

紙に書き出すとき、名詞は大きく分けて3つの種類に分類すると設計が一気にラクになります！

1. **実体（概念・モノ）** ← 最初に見つかる名詞チャンネル、番組、シーズン、エピソード、ジャンル
2. **出来事・ログ（コト）** ← 時間が絡むもの放送枠 / スケジュール（いつ放映されたか）
3. **関係性（ペア）** ← **紙には出てこない！**「多対多」の場所を探して後から足す番組ジャンル（`program_genres`）

名詞を書き出すアプローチ自体は100点満点です！

「多対多の関係（1つの〇〇が複数の△△を持ち、1つの△△に複数の〇〇が含まれる関係）を見つけたら、間にペアメモ用テーブルを挟む」というテクニックだけ覚えておけば、今後どんなDB設計でもバッチリ対応できますよ！
</details>

## ❷リレーション関係を書き出す
<details>
<summary>なぜリレーションを見つけるのか？  </summary>
結論から言うと、見つけたリレーションは次の2つのステップ（開発の現場）で決定的に活きてきます！

### 1. テーブルに「どのカラム（ID）を追加するか」が機械的に決まる

リレーションを見つけると、テーブル同士を繋ぐための「共通のID（外部キー）」をどのテーブルに持たせればいいかが自動的に決まります

```jsx
「1対多」の関係と分かったら
　　➔「多」側のテーブルに「1」側のIDを付け足す！

例: シーズン（1）対 エピソード（多）なら、episodes テーブルに season_id をカラムとして追加
```

```jsx
「多対多」の関係と分かったら
　➔お互いのIDを入れた「中間テーブル」を新しく作る！

例: 番組（多）対 ジャンル（多）なら、program_genres というテーブルを作って program_id と genre_id を入れる。
```

つまり、リレーションを見つける作業は「テーブルのカラム（枠組み）を確定させる作業」そのもの

### 2. アプリの検索・表示機能（SQLのJOIN）で大活躍する

ここが一番の醍醐味です！
アプリで「画面に情報を表示したい」となったとき、リレーションで繋いだIDを使ってデータ同士を**合体（結合 =JOIN）させて引っ張ってくることができます。

💡 実際の活用シーンの例（まさにステップ2課題！）

例えば、アプリの画面に**「『鬼滅の刃』の全エピソード一覧を表示したい」**となったとします。

```jsx
1. programs テーブル から「鬼滅の刃（id = 1）」を探す

2. リレーション（program_id）を辿って `seasons` テーブルから「シーズン1（id = 10）」を見つける

3. リレーション（season_id）を辿って `episodes` テーブルから「season_id = 10 のエピソード（1話〜26話）」を全件取ってくる！
```

この「リレーションを辿ってデータを一気に持ってくる命令」を書くのが、今回の課題のステップ2（SQLの作成）です。

### 🔑 まとめ

リレーションを見つけると、

```jsx
1. DB構築時：迷わず正しいテーブルとカラム（外部キー）が作れる！
2. アプリ開発時：「プログラムから欲しいデータを自由自在に引き出せる（SQLが書ける）」ようになる！
```

というように、設計から開発までの**「設計図」**としてそのまま活きてきます。

</details>


### リレーションを見つける手順、その後にやること

**▪️ステップ1: 書き出した名詞から「2つ」をペアにして並べる**

まずは紙に書いた名詞から、関係がありそうな2つを自由にピックアップします。

- 例: 「番組」と「ジャンル」
- 例: 「シーズン」と「エピソード」
- 例: 「チャンネル」と「番組」

**▪️ステップ2: 【超重要】2つの問いを自分に投げかける(1対多か多対多の判別)**

ペアにした2つの名詞に対して、矢印を往復させて以下の2つの質問をします。

Q1 「A（左）」は「B（右）」を複数持てる？
Q2 逆に「B（右）」は「A（左）」を複数持てる？

この「はい/いいえ」の組み合わせで、機械的に答えが出ます。

**▪️ステップ3: 質問の結果でタイプ（テーブルの作り方）を判定する**

●判定パターンA: 片方だけ「はい」（＝1対多）

```jsx
質問①（番組 ➔ シーズン）: 1つの「番組」にシーズンは複数ある？
 ➔ はい（シーズン1、シーズン2…）

質問②（シーズン ➔ 番組）: 1つの「シーズン」が複数の番組に属することはある？
 ➔ いいえ（『鬼滅の刃 シーズン1』は『鬼滅の刃』だけのもの）
```

💡 判定: 1対多（親子関係）

- 「多」になる側（シーズン）に、「1」側（番組）のIDを1つ書くだけ！
- ➔ 中間テーブルは不要！

ーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーー

●判定パターンB: 両方とも「はい」（＝多対多）

```jsx
質問①（番組 ➔ ジャンル）: 1つの「番組」にジャンルは複数ある？ ➔ はい（アニメ、アクション…）
質問②（ジャンル ➔ 番組）: 1つの「ジャンル」に番組は複数ある？ ➔ はい（『鬼滅』『SPY×FAMILY』…）
```

💡 判定: 多対多

- お互いのテーブルに書ききれないので、ペアを記録する専用テーブル（中間テーブル）を新しく作る！
- ➔ 中間テーブル（program_genres）が必要！

ーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーーー

●判定パターンC: 両方とも「いいえ」（＝1対1）

- 例: 「ユーザー」と「マイナンバーカード」
- 質問①も②も「いいえ（1つだけ）」になる関係。

💡 判定: 1対1

- 基本的には同じ1つのテーブルにまとめてしまってOK


```jsx
リレーション

●1対多（中間テーブル不要・親のIDを子に持たせる）
	1.●番組(1) ↔ シーズン(多)
	2.●シーズン(1) ↔ エピソード(多)
	3.🟡チャンネル(1) ↔ 番組枠(多)
	4.●エピソード(1) ↔ 番組枠(多)
	
●多対多（中間テーブルが必要）
	1.番組(多) ↔ ジャンル(多)
	中間テーブル: program_genres
	2.🟡チャンネル(多) ↔ エピソード(多)
	中間テーブル: 番組枠（channel_schedules）

```

<details>
<summary>疑問：仕様の階層構造（番組 ➔ シーズン ➔ エピソード ➔ 番組枠）親→子の関係に関して
なんで番組枠が階層の一番下だとわかるのか？  </summary>

結論から言うと「動画というデータが実際にユーザーの画面（テレビ）に流れる、最後の『アウトプット（出来事）』だから」

### 🎬 映画やアニメが作られて放送されるまでの流れ

現実世界でコンテンツ（アニメなど）が作られてから、テレビやABEMAで放送されるまでの流れを想像してみてください。

1. 番組を作る：まず『鬼滅の刃』という企画・作品（番組）が生まれる
2. シーズンに分ける：全何話かを「立志編」「遊郭編」などのまとまり（シーズン）に分ける
3. 動画ファイル（1本）が完成する：編集が終わって「第1話」「第2話」という実際の動画ファイル（エピソード）が納品される
4. 放送枠にセットする：完成した動画ファイルを「ドラマ1チャンネルの 8/1(土) 20:00〜20:30 の枠（番組枠）」にセットして放映する

このように「番組 ➔ シーズン ➔ エピソード」までは『動画コンテンツそのもの（作品）』**を作っている段階
そして最後に「できた動画（エピソード）をいつ・どのチャンネルで流すか」というスケジュール（番組枠）が割り当てられます。

### 💡 「番組枠が一番下」だとわかる決定的な証拠2つ

**証拠①: 番組枠がなくてもエピソードは存在できるが、エピソードがないと番組枠は存在できない**

- 制作会社で「第1話の動画データ（エピソード）」が完成・保存されても、まだテレビで放送されていなければ番組枠は0個
- 一方で、流す動画データ（エピソード）が何も決まっていないのに「番組枠」だけがポツンと存在することはあり得ません

つまり「エピソード」があって初めて「番組枠」が作れる（＝番組枠はエピソードに依存している）**ため、番組枠の方が下の階層になります。

証拠②: 「再放送」があるから
仕様書に「再放送もあるため、ある番組（エピソード）が複数の番組枠で放映される」とありましたよね。

- 1話の動画データ（エピソード）は 1本 しかありません。
- でも、番組枠は 「本放送（月曜20時）」「再放送（土曜14時）」「年末特番枠（12/31）」 と、1本の動画に対して複数（下位）に増えていきます。

1つの親（エピソード）に対して、多の子ども（番組枠）がたくさんぶら下がる形になるので、階層構造としても一番下が「番組枠」になります。
</details>




<details>
<summary>疑問：「チャンネル」と「エピソード」がなぜペアとして成立するのか？？→KPIでのシステム的な関係から必要なため  </summary>
<br>
実は「チャンネル」と「エピソード」は、現実世界では直接結びついていません。
では、なぜデータベース設計の文脈で「ペア」として登場するのか？
その答えは「サービスでやりたいこと（仕様）を実現するために、システムが裏側で関係を作っているから」

### 1. 現実世界の感覚（直感通り）

- チャンネル（例: ドラマ1チャンネル）は「動画を流す放送局/枠組み」
- エピソード（例: 鬼滅の刃 1話）は「完成した1本の動画ファイル」

この2つはただの「別のデータ」であって、お互いのデータの中に相手の情報を直接書き込むことはできません。

- チャンネルの箱に「動画データ」を直接埋め込むことはできない
- 動画データ（ファイル）の中に「どのチャンネルで流すか」を直接書き込むこともできない（だって再放送でいろんなチャンネルで流れるかもしれないから）

つまり「この2つは直接のペアではない」のです。

### 2. でも、アプリの画面ではどう見えているか？

しかし、ユーザーが ABEMA などのアプリを開いた時のことを想像してみてください。
画面にはこう表示されていますよね？

【ドラマ1チャンネルの画面】
➔ 今流れている動画：「鬼滅の刃 第1話」
ユーザーから見ると「このチャンネルで、このエピソード（動画）が流れている」という関係が確かに存在しています。

さらに、仕様書にはこう書かれていました。
「KPIとして、チャンネルの番組枠のエピソードごとに視聴数を記録する」
→つまりエピソードというのは動画単位の最小単位(番組 ➔ シーズン ➔ エピソード)で
その最小単位で視聴数(再生数)としてカウントしたいということ

つまり”システムとしては”「チャンネル A」と「エピソード B」が出会った事実（放送されたこと）を記録して、その時の視聴数を数えたいのです。
→システム的な側面からも考えるべき
