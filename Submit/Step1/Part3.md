## 以下作業しているなかでの疑問点等

<details>
<summary>疑問：キーに関してINDEXは外部キーのこと？  </summary>

結論から言うと「外部キー ＝ INDEX（の一部）」という関係です！
INDEXは外部キーだけを指す言葉ではありません。

### 💡 INDEX（インデックス）の本質は「目次」

巨大な百科事典から「鬼滅の刃」のページを探すとき、1ページ目からパラパラめくると時間がかかりますよね。でも、一番後ろにある**「あいうえお順の索引（インデックス）」**を見れば、一瞬で「350ページ！」と分かります。

データベースの INDEX もまったく同じです！

テーブルの特定の列（カラム）にINDEXを作っておくと、データを検索するスピードが劇的に速くなります。

### 🔑 PRIMARY / INDEX の違い

課題や指示書にある「PRIMARY / INDEX のどちらかを記載」というのは、こういう意味です。

| **種類** | **意味** | **どのカラムにつける？** |
| --- | --- | --- |
| PRIMARY | 主キー（データを1行に特定する背番号） | テーブルの自身の id |
| INDEX | 検索を速くするための目次 | 頻繁に検索・結合（JOIN）で使われるカラム
（★外部キーや、検索によく使う日付など） |

### ❓ なぜ「外部キー」に INDEX をつけるの？

例えば、episodes（エピソード）テーブルから「シーズン10のエピソード一覧」を取り出すとき、SQLではこう書きます。

```sql
SELECT * FROM episodes WHERE season_id = 10;
```

このとき、season_id（外部キー）に INDEX（目次） が設定されていないと、データベースは何万件もあるエピソードを最初から最後まで全件探すことになってしまいます。

そのため「外部キーのカラムには、検索を速くするために INDEX を設定しておく」のがデータベース設計の鉄則なのです！

### 💡 まとめ

提出物や設計書に書くときは、以下のように当てはめればバッチリです！

- 自分のテーブルの id ➔ PRIMARY（＋ `AUTO_INCREMENT`）
- 相手のID（program_id や season_id などの外部キー） ➔ INDEX
- その他の普通の項目（タイトルや説明など） ➔ キーの記載なし（空欄でOK）

<details>
<summary>ユニークキーの疑問：外部キーには基本ユニークキーつけるってこと？  </summary>

結論から言うと、「外部キーだからといって基本ユニークキーをつけるわけではない」というのがデータベース設計の原則です！  
「1対多（1 : N）」のケースと「1対1（1 : 1）」のケースで扱いが変わるのがポイント

### 💡 なぜ基本はユニークをつけないのか？（1対多の場合）

通常の外部キーは**「1対多」**のリレーションを作ることがほとんどです。  
たとえば、今回設計したseasons（シーズン）テーブルのprogram_id（番組ID）を見てみましょう。

- 『鬼滅の刃』（program_id = 1）には、シーズン1・シーズン2・シーズン3と複数のシーズンが存在しますよね。
- もし `program_id` 単体に `UNIQUE` をつけてしまうと、**「1つの番組には1つのシーズンしか登録できない（1対1）」**ことになってしまいます！

そのため、外部キー単体にはUNIQUEをつけず、何度も同じID（多）が登場できるようにするのが基本です。

### 🛠 ユニークキーをつけるのはどんな時？

外部キーにユニークキーをつける（または絡める）のは、主に以下の 2つのパターン だけです！

**① 【超重要】複合ユニークにする場合（今回やったパターン！）**

「外部キー単体」ではなく、「外部キー ＋ 別のカラム」のセット（組み合わせ）でユニークにするケースです。

- `program_id`（外部キー） ＋ `season_number`（シーズン番号） ＝ UNIQUE
⚬	⭕️ 番組ID「1」に シーズン「1」 ➔ OK
⚬	⭕️ 番組ID「1」に シーズン「2」 ➔ OK（`program_id` は重複してOK！）
⚬	❌ 番組ID「1」に シーズン「1」 ➔ NG！（組み合わせの重複を弾く）

**② 1対1（1 : 1）のリレーションを作る場合**

2つのテーブルを「1対1」でガッチリ結びつけたい時です。

（例：users（ユーザー）テーブルとuser_profiles（詳細プロフィール）テーブルを1対1で分ける場合など、外部キー側にUNIQUEをつけて1人1個に制限します）

### 🎯 まとめ

- 普通の外部キー（1対多） ➔ `UNIQUE` はつけない（複数登録したいから）
- 組み合わせで重複を防ぎたい時 ➔ `UNIQUE(外部キー, 〇〇)` と複合ユニークにする
- 1対1にしたい時だけ ➔ 外部キー単体に `UNIQUE` をつける
</details>



<details>
<summary>疑問：duration（動画の時間／尺）に関して動画の尺って##:##みたいな感じで：が入るイメージだったんだけど、それも可能か？  
  またその場合、実務で一般的に使われるのはどれ？  </summary>

結論から言うと、12:30 や 01:30:00 のようなコロン（:）入りの形式でデータベースに保存することも可能です！  
その場合は、文字として扱う VARCHAR(8)（例:"01:30:00"）や、時刻型である TIME 型 を使います。

### では、「INT（秒数）」と「TIME / VARCHAR（時:分:秒）」のどちらが実務でよく使われるか？

**→🏆 実務での結論：ダントツでINT（秒数）が主流です！**

実務（特に動画配信サービスや音声サービス）では、INT（秒数）で管理するケースが圧倒的に多いです！
例えば、24分30秒の動画なら 1470（秒）としてデータベースに保存します。

### 💡 なぜINT（秒数）が圧倒的に使われるのか？

**理由1：時間の計算（足し算・集計）が超ラクだから**

「このシーズンの総再生時間を計算したい」「ユーザーが今月何分動画を見たか集計したい」という時、INT（秒数）なら単純な足し算（SUM）で一瞬で計算できます。

- ⭕️ INT の場合: `1470` ＋ `1800` ＝ `3270秒`（SQLの `SUM` 一発で終了）
- ❌ 12:30 が文字列の場合: そのまま足し算ができないため、プログラミング側で「分」と「秒」に切り分けて計算し直す必要があり、めちゃくちゃ面倒になります。

**理由2：動画プレイヤーとの相性が抜群に良いから**

YouTubeやWebの動画プレイヤー（JavaScript）は、内部的に動画の長さや現在の再生位置を「秒数（またはミリ秒）」で管理しています。
データベースから1470という数値で受け取った方が、動画プレイヤーにそのまま渡せて都合が良いのです。

### 📺 じゃあ「12:30」みたいな表示はどうするの？

「データベースには 1470（秒）で保存しておき、画面に表示するときだけプログラム（JavaScriptやPython等）で 12:30 に変換して見せる」
というのが、Web開発の鉄則であり、最もスマートな方法です！

**🌸 画面・DBごとの役割分担**

- データベース（DB） ➔ 1470（`INT` 型：計算や処理がしやすい数値で持つ）
- ユーザーに見せる画面 ➔ 24:30（プログラムで変換して人間が見やすい形にする）

</details>
